Draft v1 was reviewed by a statistician persona and an fMRI-methods persona (`review-v1-statistician.txt`, `review-v1-fmri.txt`); responses in §12. ## 1. Question and what it can show
Do the permutation rules that decoding toolboxes ship and teach behave on block-design fMRI as they did on mouse spiking, human EEG and simulations, when training and test samples share blocks? The paper's Limitations say that fMRI was not tested; this step tests one public dataset, the one used in the PyMVPA tutorial.
- The fake labels are assigned at random within runs, so the block permutation test that permutes them within runs (P5) is exact by construction (§4). P5's rate is therefore an implementation check, not a finding. The measured quantity is how far the other rules exceed 5%; the primary contrast quantifies a known mechanism (block identity is decodable) on fMRI.
- Ventral temporal cortex carries strong category signal, and each fake split groups real categories differently, so the other rules can also exceed 5% through stimulus signal shared within a block, not only through slow drift. The step does not separate these sources and reports no claim about drift as such.

## 2. Data
- Haxby et al. (2001), as distributed by PyMVPA: `http://data.pymvpa.org/datasets/haxby2001/subj{1..6}-2010.01.14.tar.gz`, CC BY-SA 3.0, downloaded and checked against the server's `MD5SUMS` by `code/fetch_haxby.py` (stops on a mismatch; writes `MANIFEST.sha256` of the files used). Per subject: `bold.nii.gz` (1,452 volumes, 12 runs concatenated, not detrended; TR 2.5 s), `labels.txt` (category and run, "chunk", per volume), `mask4_vt.nii.gz` (ventral temporal mask in functional space). Nothing else is used.
- Subject 5: run 9 (chunk 8) is corrupted (distribution README); it is removed in code (`DROP = {"subj5": [8]}`) before any processing, whatever its labels, and its label counts are logged.
- Subject index for all seeds: s = subject number − 1 (subj1 → 0, …, subj6 → 5), computed from the subject name in code.

## 3. Samples, blocks, features
- Samples: volumes whose label is not `rest`, in time order. A block is a maximal run of consecutive non-rest volumes with the same category inside one run. Inclusion (decided by `prepare_haxby.py` before any decoding, with the reason written to `<subject>.json`): every run has 8 blocks, one per category, and the subject has 96 blocks (88 for subj5). Run numbers must be 0..11 (so that `DROP` removes the documented run). Any failure (missing file, wrong volume count, failed check, or an exception in the loader) excludes the subject with its reason; the results note names every exclusion and whether it came from a check or an exception.
- Features: the VT-mask voxels. Primary preprocessing (`detrended`): within each run, each voxel's time series over all volumes of the run (rest included) is linearly detrended and z-scored, then the non-rest volumes are kept (per-run detrending and z-scoring as in the PyMVPA tutorial, whose variant z-scores against the rest volumes). Sensitivity (`raw`): no detrending or z-scoring. Labels are used as distributed, without a hemodynamic shift: for fake labels the shift is irrelevant (labels carry no information), and for the positive control the first volumes of each block still carry the response to the preceding rest period, which can only weaken it.
- Volumes per block are equalized within a subject by keeping the first m volumes of each block, m = the subject's smallest block length. Classes are then balanced overall in every assignment; per-fold balance is not enforced, and the statistic is the mean of fold accuracies (step 2).

## 4. Labels with no information (fake labels)
- Within each run, 4 of the 8 blocks are assigned to class 1 at random (independently per run). Per subject, 30 assignments drawn with `numpy.random.default_rng([2026, 41, s, d])`, d = 0..29 (redrawn while equal to an earlier assignment or its class swap; each assignment is still marginally uniform over the within-run group). P5 permutes the observed block labels within runs (`engine.within_run_draw`), the same group, so it is exact for these labels.
- Other seeds: fold seed and P2 `random_state` = `default_rng([2026, 42, s, d, split index]).integers(2**31 − 1)` (shared by the two preprocessings and by the positive control, which uses d = 0); rule generator (P3, P4, P5 draws) = `default_rng([2026, 43, s, d, split index, arm flag, preprocessing index])`. Split index: main 0, tool 1, run 2, block 3.
- Positive control (pipeline check): real categories `face` vs `house`, face and house blocks only (one of each per run), `detrended`, under S-main and S-run. P5 null: within each run the two labels swapped or not (2^12 patterns; 200 drawn). Exact only if the category order was randomized across runs, which the distribution does not document ("original sequence of presentation is N/A"). If the control fails, it is reported; no preprocessing or decoder change follows.

## 5. Splits
- S-main: shuffled KFold(5) over samples (training and test share blocks).
- S-tool: unshuffled StratifiedKFold(5) (scikit-learn's default), re-split for every permuted label vector. On time-ordered samples its folds are nearly contiguous (about 2.4 runs each), so only blocks at fold boundaries are shared; it is kept as the configuration a user gets with `cv=5`.
- S-run: leave-one-run-out (`LeaveOneGroupOut`; 12 folds, 11 for subj5), the split of the PyMVPA and CoSMoMVPA tutorials. Training and test never share blocks.
- S-block: whole blocks held out, fold = block index mod 5 (`PredefinedSplit`; a fixed map, so the folds do not depend on GroupKFold's tie order, which differs between platforms; Supplementary Note 4 of the paper).

## 6. Rules (step 2 `sim.py`, unchanged; 200 draws each; statistic = mean fold accuracy)
P1 binomial test of the pooled held-out correct count; P2 scikit-learn `permutation_test_score` (labels permuted across all samples, refit; under S-tool re-split per permuted vector); P3 the CoSMoMVPA rule (labels permuted within runs at sample level, refit); P4 training labels permuted per fold, refit, test labels kept (the rule of the PyMVPA tutorial and of ADAM, `../step2-comparison/TOOLBOX-DEFAULTS.md`); P5 the block permutation test, block labels permuted within runs, training and test together, refit. p = (1 + #null ≥ obs) / (N + 1); a fold whose training labels hold one class makes the statistic undefined.

## 7. Decoder
`sim.pipeline()`: standardization, 20 voxels by F test, L2 logistic regression (C = 1), fitted on training folds only (as steps 2 and 2b).

## 8. Outcomes and decision rules (fixed now; `code/summarize.py --step 4`)
- Unit = subject. Per subject, the share of its 30 assignments with p < 0.05 (strict; undefined p values left out and counted); mean over subjects; subject percentile bootstrap 95% interval (B = 20,000; a fresh `default_rng(20261102)` for every quantity). "Inflated" = lower bound above 10%. Also reported per rule: the number of subjects with at least 5 rejections of 30 (above the 95% binomial bound under 5%).
- **Primary contrast E4:** E = 1[p_P2 < 0.05] − 1[p_P5 < 0.05] per (subject, assignment), fake labels, S-main, `detrended`; pairs with an undefined p left out and counted; mean per subject, then over subjects; "positive" = bootstrap lower bound above 0. Also reported: per-subject E and the number of subjects with E > 0 (exact one-sided binomial test over all subjects with a defined E; subjects with E = 0 are kept and count as not positive, which is conservative). With fewer than 5 subjects with a defined E no decision is made.
- Secondary (no decision): every rule under every split and both preprocessings; P3 under S-run (the CoSMoMVPA tutorial configuration) and P4 under S-run (the PyMVPA tutorial configuration); the positive control.
- The summary stops if a row is duplicated, a test row is present, a subject has no inclusion record, an included subject's key set differs from the design (240 fake and 2 control keys), a row has a number of draws other than 200, or rows come from different package versions.

## 9. Predictions (may be wrong)
1. P1, P2, P4 inflated under S-main (`detrended` and `raw`); under S-tool not predicted.
2. (Implementation check, not a prediction) P5 not inflated (bootstrap upper bound at or below 10%) under every split.
3. Under S-run, P2 and P4 lower than under S-main; whether they stay above 10% is not predicted.
4. `raw` inflates at least as much as `detrended`.
5. Positive control: P1–P4 reject in most subjects under S-main and S-run; P5 rejects in most subjects if the category order was randomized.

## 10. Compute and environment
Laptop (Apple A18 Pro, 6 cores, 8 GB), Python 3.12, numpy 2.5.4, scipy 1.18.1, scikit-learn 1.7.2, nibabel 5.3.2 (`requirements.txt`), one process per subject, `OMP_NUM_THREADS=1`. A real-sized synthetic job (577 voxels, 864 samples, 200 draws) took 15, 14, 34 and 14 s under S-main, S-tool, S-run and S-block: about 80 min per subject, about 1.5–2 h for six subjects in parallel. The number of draws, assignments, splits and rules is not reduced for time; the run is extended instead. Code: `code/fetch_haxby.py`, `code/prepare_haxby.py`, `code/engine.py` (shared with step 5), `code/run_haxby.py`, `code/summarize.py`; checks on synthetic data only in `code/test_synthetic.py` (output `test_synthetic.out`, all passed). Rows: `runs/rows.step4.<subject>.jsonl`, one JSON line per (subject, arm, preprocessing, assignment, split) with every p, the observed accuracy, P5's null accuracies, the fold seed (the rule-generator seed is recomputed from the key, §4), the number of convergence warnings, the number of draws and the package versions; resumable, with stored labels, seeds and draws checked against the recomputed ones. The runner refuses to run with other numpy or scikit-learn versions. Under S-main the fold seed is also P2's `random_state` (as in step 2), so one of P2's 200 permutations equals the fold shuffle order; negligible.
