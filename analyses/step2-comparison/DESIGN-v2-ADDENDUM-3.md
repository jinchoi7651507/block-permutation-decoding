## 2. P3 and P4 with the real tools
### 2a. Data (`code/add3_tools_data.py`)
- **Layouts (4):** L1 = the §15 primary cell (random balanced design, B = 12, L = 20, τ_s = 20, drift 1, trend 0); L2 = fixed order AABB (B = 12, τ_s = 20, drift 1); L3 = interleaved labels (B = 12, τ_s = 20, drift 0): the i.i.d. baseline of the rules (§15 iid baseline: P1 and P4 exceed 5% on independent data), not a negative control; **L4 = balanced runs** (B = 12 as 6 runs of 2 blocks, one per class, order random within each run; τ_s = 20, drift 1): the layout tool users design (every run holds every condition equally). L4 is new (added after the MVPA review).
- **Generator:** `sim.simulate2` at the calibrated level with the per-replicate unit count drawn from the Allen area sizes, exactly as `run_grid.one` (same lines and RNG order, copied; for L4 the block labels are `rng.permutation([0, 1])` per run, drawn where `run_grid.one` draws the labels). Seeds: layout j uses `default_rng([2029000 + j, rep])`; 500 replicates per layout (2,000 files). Each replicate is written once, atomically, to `runs_add3/tools/data/L{j}_r{rep:03d}.mat` (samples × units counts, targets 1/2, chunks = runs, blocks); a SHA-256 manifest of all 2,000 files is written before any tool runs and checked after the copy back.
- **Runs (chunks):** L1–L3: 4 runs of 3 consecutive blocks (the §15 P3 definition); L4: 6 runs of 2 blocks. In L1 a run of three blocks often holds one class only: 438 of the 924 balanced assignments (47.4%) have such a run, a known constant that the 500 replicates only estimate; CoSMoMVPA then stops with an error and the P3 port returns None. This share reflects cutting a random 12-block design into runs of three; tool users design around it (L4). P5 on the surviving L1 replicates is conditional on that pattern and is reported with this caveat.
- **Scope:** samples are single trials (MEG/EEG/electrophysiology practice). Block-design fMRI users classify one estimate per block per run, where a within-run permutation is a block-label permutation; that case is not tested here and the results are not claimed for it.

### 2b. Rows
- **CoSMoMVPA building blocks in the documented loop** (Octave 8.4, CoSMoMVPA fe5acaf checked out; CoSMoMVPA ships no single-subject permutation function: FAQ "There is no function for within-subject significance testing; through cosmo_randomize_targets and a ``for``-loop the user can do that themselves", `toolbox-src/cosmo_faq_l580-600.rst`; example `toolbox-src/cosmo_run_permutation_test.m`). Per replicate: `cosmo_nfold_partitioner` (leave one chunk out), `cosmo_crossvalidation_measure` with `cosmo_classify_lda` (regularisation 0.01, `toolbox-src/cosmo_classify_lda.m`), accuracy. The measure refuses unbalanced partitions; its error text (`toolbox-src/cosmo_check_partitions.m` l. 171–198) begins "Unbalance in partition …, classes … Consider the following scenarios: (1) the input is an MEEG dataset, or an fMRI dataset with missing samples (trials) in some of the runs. You probably want to use cosmo_balance_partitions." This is followed: `cosmo_balance_partitions` with defaults (one repeat, balanced test sets, seed 1; `toolbox-src/cosmo_balance_partitions.m`), applied to the observed dataset and again to every permuted dataset (the balanced subsets are index sets that permuted targets would unbalance; the FAQ's own null loop recomputes the partitions per null dataset, `toolbox-src/cosmo_faq_l1150-1200.rst` (FAQ l. 1183), although that example is a between-participants searchlight with unique chunks and `cosmo_independent_samples_partitioner`, not a within-run single-subject example). With a seeded balancer the statistic is one fixed function of (samples, targets, chunks), so the within-chunk permutation test stays valid (statistician review). The alternatives were checked: `'check_partitions', false` (the option the measure forwards; scenario (4) of the error names the equivalent `unbalanced_partitions_ok`) does not help, because `cosmo_classify_lda` itself stops on unequal class counts ("Different number of classes (100 and 80) - this is not supported … consider using cosmo_balance_partitions"; synthetic test, §3), so with this classifier balancing is forced. Null: 200 draws of `cosmo_randomize_targets(ds, 'seed', 1000 × rep + i)` (within-chunk permutation; error if a chunk lacks a target), whole cross-validation rerun; p = (1 + #{null ≥ observed}) / 201 (the documentation example uses #{null > observed} / n; ours counts ties against rejection). Variants: **main**; **zscore** = every feature z-scored within each run before the analysis (the per-run normalisation users apply). The `unbal` option of the script is not run (it fails with LDA, see above). Another CoSMoMVPA route exists: scenario (2) of the error text sends MEEG users with independent trials to unique chunks and `cosmo_independent_samples_partitioner`, where `cosmo_randomize_targets` permutes all labels (`cosmo_rand.m`, between-participants branch); that is the P2 rule, already covered by the stamped grid. Chunk = run is therefore one CoSMoMVPA route, not the only one. Script `code/add3_cosmo.m`.
- **PyMVPA 2.6.5** (Python 3.9; numpy 1.21.6, scipy 1.7.3, scikit-learn 1.0.2; built from source with its bundled libsvm extension; scipy ≥ 1.8 breaks the import): the tutorial's test (`toolbox-src/pymvpa_tut.rst` l. 256–330): `LinearCSVMC()`, `NFoldPartitioner(attr='chunks')`, `AttributePermutator('targets', limit={'partitions': 1}, count=1)` chained after the partitioner (training-partition labels permuted once per fold), `MCNullDist(Repeater(count=200), tail='left')` on the mean error. The 2.6.5 sources (`toolbox-src/pymvpa-2.6.5/`) differ from the master copy only in Python 2/3 syntax (`xrange`, `zip`). **p_tool** = the tool's p = #{null error ≤ observed error} / n, clipped to [1/(n + 2), (n + 1)/(n + 2)] (`Nonparametric`, correction 'clip', stats.py l. 91–110); **p_mc** = (1 + k)/(n + 1) from the saved null (k = #{null ≤ observed}), so p-grid differences from the reference rows are visible. Seed: `mvpa2.seed(1000 × rep + 7)` before each replicate. The exact G4 confirms that the regenerated draws equal the tool's when the classifier is the scikit-learn adapter; for `LinearCSVMC` (libsvm) this assumes the global NumPy state is not used before the null loop (not checked separately). Variants: **main**; **zscore** = `mvpa2.mappers.zscore.zscore(ds, chunks_attr='chunks')` first (per-run z-scoring, the mvpa2 default); **chunks** = the tutorial's whole-dataset form (l. 162) with `AttributePermutator('targets', strategy='chunks', chunk_attr='blocks', count=200)` as the `MCNullDist` generator on the plain cross-validation: one permutation of whole blocks per draw, shared by all folds, training and testing together (PyMVPA's block-level option; it ignores `limit`). This is the tool's analogue of P5 in L1 and L2; in L4 it permutes across all 12 blocks, not L4's within-run randomisation (draft 2 wired it inside the fold chain, which draws a separate permutation per fold and is not a randomisation test of the statistic; corrected after the statistician's re-review). Script `code/add3_pymvpa.py`.
- **Reference rows** (Python, stamped `sim.py` functions unchanged; `code/add3_reference.py`): leave-one-run-out folds and the stamped pipeline; P3 port, P4 port, P5 = block labels permuted between blocks, training and held-out together, rerun, with 200 fresh draws from each layout's randomisation set (L1, L2: any balanced assignment of the 12 blocks, `balanced_draw`; L4: the order of the two blocks of each run flipped at random, the L4 design's own randomisation, 2^6 = 64 assignments, 32 distinct statistic values under label swap with fixed folds, so the observed value recurs in about 2 of 64 draws and the smallest attainable p is about (1 + 200 × 2/64)/201 ≈ 0.036: P5 in L4 can reject at 0.05 but coarsely: its expected size is about (0.9 + 0.2 + 0.01)/32 ≈ 3.5%, not 5% (statistician re-review), so "tool minus P5" there is read with this in mind and every L4 row is also reported minus 5%; not a power comparison; undefined in L3). One rng `default_rng([2029000 + j, rep, 5])` shared by P3, P4, P5 in that order (P4's draws depend on whether P3 errored; harmless).
- **Outcome (`code/add3_summarize_tools.py`, written before any row exists):** per layout and row: rows present, usable, errors; rate A = rejections (p < 0.05) / usable with the Monte Carlo 99% band at that n; rate B = rejections / 500 (errors and missing as non-rejections); paired difference to P5 on the same replicates (survivors, and all with errors as non-rejections), 95% bootstrap interval (B = 10,000); difference to the same row's L3 rate (unpaired bootstrap). "Inflated" = rate above the band and above the row's L3 rate (interval excluding 0).
- **Headline comparisons (fixed now, before any row exists):** in L4, CoSMoMVPA and PyMVPA, each in the main variant (as shipped, no preprocessing) and in the zscore variant (the per-run normalisation an L4 user would apply), each minus P5 and minus its L3 rate. Everything else (L1, L2, the variants, the ports) is descriptive. Tool rows (raw counts, LDA or SVM) and port rows (standardised, feature-selected logistic regression) are compared descriptively only; port rows are never labelled with a tool's name in figures. No text will say that a toolbox is wrong: the tutorials' rules are valid where conditions are exchangeable within runs; the question is trial-level samples under within-run drift.
- **Error classes (pre-specified):** the only expected errors are CoSMoMVPA errors in L1 on replicates where the P3 port also returns None. Any other error (any PyMVPA error; any error in L2, L3 or L4; a CoSMoMVPA error where P3 is defined) or any missing row makes the run incomplete: investigated, fixed and rerun, never reported as a result. Each error message is written into the row.

### 2c. Agreement gate (L2 replicates 0–49, where every run holds both classes; reported, does not stop the run)
- **G1, CoSMoMVPA rule:** every permutation the tool returns in the main L2 run (the `permutation` output of `cosmo_randomize_targets`, saved for replicates 0–49) keeps each sample in its chunk and each chunk's multiset of targets (pass = 100%). **G1b:** on a constructed dataset whose first chunk holds one class, the tool stops with an error and `p3_within_run` returns None. (G1 reads files written by the main tool run, so it is evaluated after 2b.)
- **G2, PyMVPA rule:** with the draws regenerated from each replicate's seed (the same sequence as in the tool run), the permuted targets equal the observed ones on the testing partition and are a permutation of them on the training partition for every fold and draw (pass = 100%); each fold's test chunk is saved and asserted equal to the order of `loro_folds` (1, 2, 3, 4).
- **G3, PyMVPA wiring:** the stamped pipeline in `SKLLearnerAdapter` through PyMVPA's `CrossValidation` equals a plain scikit-learn leave-one-run-out loop in the same Python 3.9 environment (observed accuracy, 50 replicates, ≤ 1e-12). It checks the adapter path, not `LinearCSVMC`.
- **G4, exact rule check (replaces the draft-1 tolerance):** on L2 replicates 0–9, PyMVPA's full `MCNullDist` with `SKLLearnerAdapter(pipeline)` gives the same 200 null errors and observed error as a plain scikit-learn loop over the regenerated draws (≤ 1e-12, same environment). Descriptive only: for the 50 replicates, the P3 and P4 port p values with the tools' draws against those with the ports' own draws (rng [2029002, rep, 9]). The P3 port matches the tool's permutation rule, not its pipeline (no balancing subsampling).
- A gate failure is reported with its cause; the tool rows are still reported as "tool as shipped", and the ports are then not described as the tools' rules.
